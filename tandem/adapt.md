# TANDEM 적응 지시서

너는 TANDEM 하네스를 **이 프로젝트에 맞게 적응시키는** 세션이다.
설치 스크립트가 파일은 이미 배치했다. 네 일은 **환경 확인, 프로젝트 맞춤, 검증**이다.

`tandem/config.json`에 설치 스크립트가 감지한 값이 있다. 먼저 읽는다.
문서 경로는 그 파일의 `docs_root` 값이다. 아래에서 `<DOCS>`는 그 값을 뜻한다.

## 원칙

1. **기존 체계가 이긴다.** 이 프로젝트에 이미 문서 구조, ID 체계, 규칙 파일, 스킬이 있으면
   TANDEM 쪽을 거기에 맞춘다. 반대가 아니다. 새 ID 체계를 만들지 마라.
2. **기존 파일을 덮어쓰지 않는다.** 설치 스크립트가 `.new`로 남긴 것이 있으면 병합안을 제시하고,
   실제 병합은 사람 승인 후에 한다.
3. **확인하지 않은 것을 문서에 확정으로 쓰지 않는다.** 특히 모델 ID와 CLI 플래그.
   확인 못 한 항목은 "확인 불가"로 남긴다.
4. **커밋하지 않는다.** 사람이 확인하고 직접 커밋한다.

## 시작 전

`git status`로 작업 트리를 본다. 커밋 안 된 변경이 있으면 알리고 진행 여부를 묻는다.
git 저장소가 아니면 되돌리기 수단이 없다는 사실을 알린다.

---

## 1단계: 프로젝트 파악

읽는다.

- `tandem/config.json`
- 루트의 `README.md`, `CLAUDE.md`, `AGENTS.md`, `.gitignore`
- `.claude/` 전체 (settings, agents, commands, skills, hooks)
- `.codex/`, 전역 `~/.codex/config.toml`, 전역 `~/.claude/`
- 프로젝트 문서 폴더 (`docs/`, `doc/`, `documentation/` 등 있는 것)
- 이 세션에서 쓸 수 있는 스킬 목록

정리한다.

| 항목 | 찾을 것 |
|---|---|
| 프로젝트 성격 | 무엇을 만드는 프로젝트인가. 언어, 스택 |
| 기준 문서 | 단일 진실 공급원 역할을 하는 문서가 있는가. 누가 고치는가 |
| ID 체계 | 과제, 결정, 이슈에 쓰는 ID 형식이 있는가 |
| 인수인계 | 세션 간 상태를 넘기는 방식이 있는가 |
| 기존 역할 | 이미 쓰는 서브에이전트, 스킬, 커맨드 |
| 문체 규칙 | 언어, 어투, 금지 사항 |
| 이름 충돌 | `tandem-*` 역할/커맨드와 겹치는 기존 것이 있는가 |

## 2단계: 환경 확인

추측으로 채우지 마라.

1. `claude --version`
2. `codex --version`. **Codex CLI가 없으면 여기서 멈추고 보고한다.**
   설치 없이는 이 하네스가 동작하지 않는다.
3. **이 계정에서 실제로 쓸 수 있는 Codex 모델 목록과 정확한 ID.**
   최상위 / 중상위 / 경량 세 층으로 분류한다.
   설치 스크립트가 넣은 자리표시자 값을 **전부 실제 ID로 교체한다.**
   최상위가 계정에서 막혀 있으면 승급 경로를 다시 설계한다.
4. `codex exec --help` — 실제 플래그: `-m/--model`, `--sandbox`, `--output-last-message`,
   `--profile`, `--search`
5. 지원하는 추론 강도 값과 모델별 차이
6. Codex 웹 검색 동작 여부
7. Codex가 `AGENTS.md`를 읽는지, 탐색 우선순위
8. 이 OS에서 샌드박스가 정상 동작하는지

## 3단계: 프로젝트 맞춤

배치된 파일을 고친다. 대상은 `<DOCS>/` 아래 전부, `.claude/agents/tandem-*.md`,
`.claude/commands/tandem*.md`, `.codex/`, 그리고 `.new` 파일들이다.

- **모델 ID를 2단계에서 확인한 실제 값으로 전부 교체한다.**
  `model-routing.md`, `.codex/config.toml`, `.codex/agents/*.toml`, `delegation.md`의 예시 명령,
  `harness-status.md`까지 빠짐없이.
- **`<DOCS>/operating-model.md`의 "프로젝트 기준 문서" 표를 채운다.**
  1단계에서 찾은 문서를 넣는다. 없으면 "기준 문서 없이 운영"이라고 명시한다.
- **"되돌리기 어려운 결정" 목록을 채운다.** 이 프로젝트에서 무엇이 여기 해당하는지.
  이게 `tandem-critic` 호출 기준이 된다.
- **과제 ID 형식을 기존 체계에 맞춘다.** 템플릿의 `T-12` 예시를 프로젝트 형식으로 바꾼다.
  기존 체계가 없으면 하나를 정하고 `operating-model.md`에 적는다.
- **문서 경로를 기존 구조에 맞춘다.** `docs_root`가 프로젝트 구조와 안 맞으면 옮기고,
  **모든 파일의 경로 참조를 함께 고친다.** `config.json`의 `docs_root`도 갱신한다.
- **`lead-charter.md` 6절 판정 기준에 프로젝트 고유 기준을 덧붙인다.**
- **문체 규칙을 맞춘다.** 프로젝트가 영어면 문서도 영어로 옮길지 묻는다.
- 이름 충돌이 있으면 `tandem-` 접두사를 유지한 채 다른 이름으로 바꾸고 참조를 전부 고친다.
- 기존 스킬이 역할과 겹치면 역할 파일에서 그 스킬을 쓰도록 지시한다.
- `.codex/config.toml`이 전역 설정과 충돌하지 않는지 확인한다.
- `CLAUDE.md` / `AGENTS.md`가 같은 규칙을 두 벌로 들고 있지 않게 한다.

## 4단계: 검증

1. `.claude/settings.json`이 유효한 JSON인지. 권한 문법 경고가 있으면 고친다.
2. `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`가 `"0"`이고 상위 설정에서 `"1"`로 덮이지 않는지.
3. `CLAUDE_CODE_SUBAGENT_MODEL`이 역할 파일의 `model` 지정을 무시하지 않는지.
   **`tandem-manager`가 상위 모델로, `tandem-dispatch`가 경량으로 뜨는 것이 이 구조의 전제다.**
   강제 설정이 걸려 있으면 해제하고 보고한다.
4. `/agents`로 `tandem-manager`, `tandem-dispatch`, `tandem-critic`이 인식되는지.
5. `.codex/config.toml`이 유효한 TOML이고 프로파일 4종이 인식되는지.
6. 배치된 모든 파일의 경로 참조가 실제 존재하는 파일을 가리키는지.
7. `<DOCS>/log/runs.jsonl`이 존재하고 쓰기 가능한지.
   `.gitignore`가 이 파일을 제외하고 있지 않은지. **커밋 대상이다.**
8. `.gitignore`에 `.codex-last/`가 있는지.

## 5단계: 스모크 테스트

프로젝트 내용을 결정하는 과제는 쓰지 마라. 각 단계 결과를 기록한다.

### A. Codex 하위 일꾼 편성 (가장 중요)

작고 안전한 과제 카드를 하나 만든다. 예: "이 저장소의 최상위 폴더 구조를 표로 정리한다.
조사 부분과 정리 부분을 나눠 하위 일꾼에게 맡겨라." 판단이나 결정은 요구하지 않는다.

`tandem-dispatch`로 R1을 돌리고 확인한다.

- 하위 일꾼이 **실제로 떴는가** (로그, parts 폴더 생성 여부)
- 일꾼이 **파일에 결과를 썼는가**
- 리드가 그걸 모아 산출물 하나를 완성했는가
- `git status`로 **지정 범위 밖 파일이 변경됐는지**
- 전달책이 **본문이 아니라 경로와 요약만** 반환했는가

하위 일꾼 편성이 안 되면 그것도 결과다. 단독 실행으로 대체하는 안을 보고서에 적는다.

### B. 적대 검토 모델 분리

R2를 돌린다.

- R1과 **다른 모델**로 실행됐는가
- 약점 3개와 심각도가 들어 있는가
- 읽기 전용 샌드박스에서 파일 쓰기 시도가 없었는가

### C. 로그 기록

`<DOCS>/log/runs.jsonl`을 연다.

- **줄이 2개 이상 쌓였는가** (A의 R1, B의 R2)
- 형식이 `<DOCS>/log/README.md`와 맞는가
- `model`과 `effort`가 **실제 실행값**과 일치하는가
- B의 줄이 A와 다른 모델을 기록하고 있는가
- 한 줄이 한 JSON인가

로그가 안 쌓였으면 `tandem-dispatch`의 로그 지시를 고치고 다시 확인한다.
**로그가 안 되면 이 하네스의 자기개선 경로가 통째로 막힌다.** 통과할 때까지 잡는다.

### D. 계층

`tandem-manager`를 호출해 A의 산출물을 검수하고 종합하게 한다.
그리고 로그를 집계해 배치 소견을 내게 해 본다 (2줄뿐이라 결론은 무의미하다. **명령이 도는지**만 본다).

- 팀장이 **요약만 읽고** 판단했는가
- 종합이 지정 형식을 따르는가
- 집계 명령이 오류 없이 도는가

문제가 있으면 고친 뒤 **1회만** 재시도한다. 계속 실패하면 원문을 보고하고 멈춘다.

## 6단계: 하네스 현황 채우기

`<DOCS>/harness-status.md`의 빈칸을 **전부** 채운다. 추측 금지. 확인 못 한 건 "확인 불가".

- 적응 완료를 "예"로 바꾼다
- 활성 역할표의 Codex 쪽 모델 ID
- 확정된 모델 배치 3층과 최상위 사용 가능 여부
- 환경 확인 결과 표 전부
- 변경 이력에 적응 줄 추가

`tandem/config.json`의 `models`와 `docs_root`도 최종값으로 갱신한다.

**이 파일이 다음 세션의 시작점이다.** 비어 있으면 다음 세션이 상태를 모른다.

## 7단계: 적응 보고서

`<DOCS>/reports/setup/tandem-adapt.md`에 쓴다.

```
## 요약 (5줄 이내)
## 프로젝트 파악 결과
## 환경 확인
| 항목 | 결과 | 문서 반영 |
## 확정된 모델 배치   ← 실제 ID로 채운 최종본
## 프로젝트 맞춤 내역
| 대상 | 무엇을 | 왜 |
## 이름 충돌과 처리
## .new 파일과 병합안
| 파일 | 차이 | 병합안 |
## 검증 결과 (항목별 통과/실패/확인 불가)
## 스모크 테스트 (A 하위편성 / B 모델분리 / C 로그 / D 계층)
## 결정할 것
```

**결정할 것에 최소한 다음을 올린다.**

1. **확정된 모델 배치.** 실제 ID 3층과 승급 조건. 최상위를 쓸 수 있는지, 쓴다면 조건.
2. **적대 검토 방식.** 별도 세션만 쓸지, 하위 일꾼 지정도 쓸지 (2단계 결과 기준).
3. **Codex 쓰기 권한 범위.** `workspace-write`로 직접 쓰게 할지, `read-only`로 두고 전달책이 옮길지.
4. **`tandem-critic` 호출 조건.** 이 프로젝트에서 "되돌리기 어려운 결정"이 무엇인지.
5. **`.new` 파일 병합 여부.**
6. 2단계에서 "확인 불가"로 남은 항목의 처리.

## 8단계: 보고하고 멈춘다

채팅으로 8-12줄 보고한다: 프로젝트 파악 요지, 확정된 모델 배치,
스모크 테스트 A/B/C/D 결과, 문제가 된 항목, 결정할 것.

그리고 총괄 세션 시작 명령을 안내한다. 경로를 바꿨으면 바뀐 경로로.

```powershell
claude --append-system-prompt-file .\<DOCS>\lead-charter.md
```

세션이 뜨면 `/model`에서 총괄 모델을 선택한다고 덧붙인다.
**커밋하지 않는다.** 커밋 메시지 제안은 해도 된다.
보고 후 지시를 기다린다.
